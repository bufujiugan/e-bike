# BIKE PDA 1.0.2 / 102 · 608 扫码与打印修复

## 已确认的依据

- 用户 19.63 秒视频约第 10 秒出现 `##55UP`，随后提示“整车不存在”。这是控制回包进入车辆校验，不是真实条码的识别成功。忽略此前的英文提示。
- `tmp/demo608-硬/app/src/main/java/com/qs/utils/PrintUtils.java` 的解码出口过滤 `##55` / `##56` 等控制帧。原 UniApp AAR 的解码出口没有这层过滤。
- 同一 Demo `printBitmap` 使用 `1D 23 53 D1 7A F8 4D` 起始、点阵、标签走纸 `1D 0C`、`1D 23 45` 结束。原 AAR 开启一票一控，却没有在位图发送时添加起止指令。
- 旧点阵缓冲仅分配 `width * height / 8 + 1200`，不足以覆盖所有 570 点宽 / 非24倍数高的标签；新实现保留 ESC * 24点列格式，精确分配完整行所需空间。

## 本轮变更与范围

1. `native-compat/Qs608Protocol`、`Qs608Hardware.onDecodedScan` 在解码后过滤控制/状态回包，清空对应缓冲；只对真实条码发应用内广播和提示音。`common/scan-payload.js`、`device.js` 再做入口防护。业务校验与入库规则不变。
2. 扫码沿用厂商 GPIO167、100ms 延迟和 `1B23233535444E` 指令；错误记录异常栈并反馈。页面收到有效码才结束等待，只有控制回包则提示未收到有效码。
3. 打印保持厂商 Paper 位图绘制、80mm/570点限制；补齐一票一控封包，精确点阵长度，不截断标签，不缩小条码。
4. 串口沿用原 SDK 单例、230400波特率、1000字节分包、忙电平控制。发送队列明确处理10秒持续忙和IO异常，部分写入失败后锁住发送，不自动重试。
5. 新增 `Qs601Module.preparePrint(callback)`，保留既有公开方法签名；JS 查询 `hardwareStatus` 中的打印序号与状态。`SENT` 仅表示字节已写入串口，不能当作实物成功，不自动上报业务任务成功。
6. 默认使用用户已确认的80×100mm / 570点 / 203DPI。旧版80mm、未记录高度的设置在读取时兼容到该版式，保留终端、起始偏移、纸张模式，不覆盖存储；明确选择其他纸型的配置保留。
7. 设置页标识 `1.0.2 / 608-2`。原厂 AAR、1.0.0/1.0.1 APK、发布签名保留。此次没有修改 bike-server、数据库或旧 PDA 网站。

## 兼容与回滚

必须整体安装APK，不能只热更新JS。新JS依赖原生 `preparePrint` 和 `608-2` 状态；旧JS也不能直接配此AAR绕过打印准备。需要回滚时从保留的旧源码/原厂资料生成更高 versionCode 的纠正版本并使用原签名；不要要求操作员卸载而丢失草稿、凭据与打印防重记录。

## 安装后最短验收

1. 使用原签名覆盖安装1.0.2，不卸载BIKE PDA。暂时强制停止厂商Demo，避免同时占用串口；不自动卸载厂商Demo。
2. 设置页确认显示1.0.2 / 608-2，纸张80×100、570点、203DPI、间隙标签定位；保留本机终端编号和已校准偏移。
3. 先点“扫码自检”：确认扫描灯启动、读出真实标签内容，不能出现 `##55UP`，不会提交入库。
4. 点“打印自检标签”：检查完整出纸、底部不截断、无多走一张，再扫码读取 `BIKE-PDA-SELF-TEST`。自检不领取服务器任务。
5. 自检通过后用真实整车聚合码验证入库；必须选中仓库和库位。视频中“暂无可选记录”不能用跳过校验解决。打印原任务如果已有发送记录，先核对实物与任务状态，禁止直接重打。
