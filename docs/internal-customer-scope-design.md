# 内部客户授权范围缺口与实施边界

PRD 2.3要求内部业务员仅访问授权客户/订单。现有businessOwner文字、代理商范围和售后公司授权都不能替代该要求；本文件为实施设计，尚未完成代码。

## 授权模型

使用独立用户—客户关系和独立全客户范围权限。功能权限决定能否执行操作，客户范围决定能对谁执行；管理员仍可管理全部。代理商和PDA身份限制必须先于内部权限判断。授权修改需内部独立管理权限、请求版本、原因、审计及用户父行锁；默认不从负责人文字推断授权。

迁移须明确现有内部岗位策略，避免默认把所有PI_WRITE用户继续当作全范围。真正需要全范围的财务、仓库等岗位由明确的全范围权限授权；普通销售测试必须使用至少两个客户、两个销售用户和一次撤权。

## 必须统一覆盖的入口

| 数据 | 入口及旁路 |
| --- | --- |
| 客户 | 主资料列表、商务资料读写、PI/订单选择器、批量导出 |
| PI | 列表与总数、选项、详情、创建/编辑/取消/确认、修订历史/克隆、模板预览/固定文件/任务、商品图片/确认附件 |
| 收款和物流 | 收款登记/撤回/凭证、物流增改/历史/撤回/附件、实际出库批次详情 |
| 订单与锁 | 销售订单列表/详情/编号查询/增改/确认/取消、锁列表/编号/转单/释放、PI原子转换/锁选项、续占用/关闭剩余 |
| 通用查询 | modules/orders/customers/inventory-locks、DATA_EXPORT、业务看板、日志及搜索，不能通过总数或关键词匹配推断隐藏客户 |
| 车辆追溯 | 当前客户/历史出库/订单号与PI信息；仓库作业所需字段与商务信息应分别遵守角色和范围 |

列表必须在SQL分页和计数之前限定范围；详情和每个写入口必须后端校验，不能依赖前端选项。直接ID、同系列不同版本、附件对象ID以及第三方误授内部权限均须拒绝越权。后台到期和归档任务使用服务器保存的业务身份，不能因缺少请求线程而获得意外访问或停摆。

## 验收要求

两销售各授权一个客户，另设全范围岗位；验证所有入口的可见记录和总数一致。撤权后重新请求立即拒绝；同客户不同代理不能突破代理限制。授权和业务写入并发须有明确的事务顺序。审计失败整体回滚。旧业务数据、已发布快照与库存在范围变更时保持不变。
