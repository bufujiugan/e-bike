售后案例申报/查询管理系统需求

一、项目目标

希望开发一套类似 Avinox 合作伙伴门户的售后案例管理系统，主要用于 e-bike / 自行车售后问题的申报、审核、维修方案、配件补发、物流追踪和案例归档。

核心目标是：

客户/经销商可以直接登录系统提交售后案例，而不是通过 WhatsApp、邮件或微信把信息发给我们，再由公司内部人工整理。

理想流程：

客户登录系统
→ 新建售后案例
→ 填写车辆信息和故障信息
→ 上传图片/视频/文件
→ 提交案例
→ 公司后台收到案例
→ 售后审核
→ 技术确认维修方案
→ 如需补发配件则安排发货
→ 客户查看物流及处理进度
→ 问题解决
→ 案例完成并归档


二、系统角色

系统主要分为客户/经销商端和公司后台。

1. 客户/经销商

主要权限：

- 登录自己的账号
- 提交售后案例
- 查看自己提交的案例
- 查看售后处理进度
- 回复售后人员
- 上传图片、视频、PDF及其他文件
- 查看维修方案
- 查看补发零件及物流信息
- 查看历史售后记录

不同客户只能查看自己公司的数据，不能查看其他客户的数据。

2. 销售人员

主要权限：

- 查看自己负责客户提交的售后案例
- 查看案例状态和处理进度
- 查看客户沟通记录

3. 售后人员

主要权限：

- 查看客户提交的案例
- 审核案例
- 修改案例状态
- 回复客户
- 添加售后处理方案
- 提交技术审核
- 添加补发配件信息

4. 技术人员

主要权限：

- 查看故障信息
- 查看图片、视频、诊断报告
- 填写技术判断
- 填写维修方案
- 要求客户补充资料

5. 仓库人员

主要权限：

- 查看需要补发零件的案例
- 查看零件名称及数量
- 填写快递公司
- 填写物流单号
- 填写发货时间

6. 管理员

主要权限：

- 查看所有客户和所有案例
- 创建及管理客户账号
- 创建内部员工账号
- 设置不同角色权限
- 修改案例
- 查看统计数据


三、客户端主要菜单

客户登录以后，希望至少包含以下模块：

服务与支持

下面包含：

1. 案例申报
2. 案例查询
3. 售后支持资料 / 知识库

知识库可以作为后期功能，第一版可以暂时不做。


四、案例申报

客户点击“新建售后案例”以后填写售后申请。

建议包含以下信息。


1. 客户信息

- 公司名称
- 联系人
- 联系电话
- Email
- 国家
- 省/州
- 城市
- 详细地址
- 邮政编码

如果客户账号里面已经保存这些资料，创建案例时自动带出，不需要客户重复填写。


2. 车辆信息

- 产品型号
- 车架号 / Frame Serial Number
- 电机序列号
- 电池序列号
- 仪表序列号
- 购买日期
- 最终客户购买日期
- 是否在保修期内

如果以后售后系统与整车扫码溯源系统打通，希望客户输入或扫描车架号以后，可以自动带出该车辆绑定的：

- 电机
- 电池
- 仪表
- 产品型号
- 生产日期
- 出库日期


3. 故障信息

- 故障类型
- 故障部件
- Error Code / 故障代码
- 问题描述
- 故障发生时间
- 已尝试过的维修方法

故障类型建议做成下拉菜单，例如：

- 电机
- 电池
- 仪表
- 控制器
- 车架
- 后三角
- 前叉
- 后避震
- 刹车
- 变速系统
- 轮组
- 其他


4. 图片和附件

客户可以上传：

- 故障图片
- 故障视频
- 车架号照片
- 电机序列号照片
- 电池序列号照片
- 仪表序列号照片
- 购买凭证
- 诊断报告
- PDF
- 其他附件

希望支持多个文件同时上传。


5. 提交案例

客户填写完成以后点击：

“提交案例”

系统自动生成唯一案例编号。

例如：

TW-AS-20260905-0001

案例编号不能重复。


五、案例状态及流程

参考 Avinox 的方式，希望每一个案例顶部都有一个明显的状态进度条。

状态建议：

待提交
→ 已提交
→ 审核中
→ 已审批
→ 处理中
→ 已发货
→ 完成

具体说明：

1. 待提交

客户已经创建案例，但还没有正式提交。

2. 已提交

客户已经提交售后申请，等待公司处理。

3. 审核中

售后或技术人员正在审核故障和保修责任。

4. 已审批

已经确认售后解决方案。

5. 处理中

例如：

- 等待客户测试
- 等待客户补充资料
- 等待配件
- 等待维修
- 等待仓库发货

6. 已发货

补发零件已经寄出。

7. 完成

售后问题已经解决，案例关闭。

后台人员修改状态后，客户可以实时看到最新状态。


六、案例查询

客户和后台都需要有“案例查询”功能。

案例列表建议显示：

- 案例编号
- 创建时间
- 客户名称
- 产品型号
- 车架号
- 故障类型
- 当前案例状态
- 保修状态
- 售后负责人
- 最后更新时间

支持搜索和筛选。

建议可以按照以下条件搜索：

- 案例编号
- 客户名称
- 联系人
- 车架号
- 产品型号
- 故障类型
- 国家
- 创建时间
- 案例状态
- 售后负责人

案例查询页面可以增加快捷分类：

- 待处理
- 审核中
- 处理中
- 等待客户回复
- 待发货
- 已发货
- 已完成

点击案例以后进入案例详情页面。


七、案例详情页面

参考 Avinox 页面设计。

页面顶部显示：

案例编号

例如：

案例：TW-AS-20260905-0001

下面显示案例进度：

已提交
→ 审核中
→ 已审批
→ 已发货
→ 完成

案例详情建议分成多个 Tab。


Tab 1：工单信息

显示：

基本信息：

- 案例编号
- 案例类型
- 保修 / 非保修
- 案例状态
- 审核状态
- 创建时间
- 最后更新时间

客户信息：

- 公司名称
- 联系人
- 电话
- Email
- 国家
- 地址
- 邮政编码

车辆信息：

- 产品型号
- 车架号
- 电机序列号
- 电池序列号
- 仪表序列号
- 购买时间

故障信息：

- 故障类型
- 故障部件
- Error Code
- 问题描述
- 已尝试维修方案

附件：

- 图片
- 视频
- PDF
- 诊断报告
- 其他文件


Tab 2：维修方案

由公司售后或技术人员填写。

包含：

- 故障判断
- 技术人员意见
- 故障原因
- 维修方法
- 是否需要更换零件
- 更换零件名称
- 零件数量
- 是否免费
- 客户需要执行的操作
- 技术附件
- 维修说明

例如：

“请先更换电机进行交叉测试，如果问题仍然存在，请上传诊断工具生成的报告。”


Tab 3：发运信息

如果需要补发零件，可以填写：

- 补发零件名称
- 零件编号
- 数量
- 发货仓库
- 收货人
- 联系电话
- 收货地址
- 邮政编码
- 快递公司
- Tracking Number
- 发货日期
- 预计到达日期
- 物流状态

客户可以直接在系统里面查看物流信息。


Tab 4：变更记录

系统自动保存所有操作记录。

例如：

2026-09-05 10:30
客户提交案例

2026-09-05 14:20
Nia 将案例状态修改为“审核中”

2026-09-06 09:30
技术人员添加维修方案

2026-09-08 15:20
负责人审批通过

2026-09-09 11:00
仓库添加 DHL 运单号 XXXXX

所有记录应该包含：

- 操作时间
- 操作人员
- 操作内容

历史记录不能随意删除。

这样即使以后负责员工离职，也可以查看完整的售后处理历史。


Tab 5：旧件处理

如果售后补发了电机、电池、仪表等零件，需要记录旧件是否需要退回。

建议状态：

- 无需退回
- 需要退回
- 等待客户寄回
- 客户已寄出
- 公司已收到
- 已检测
- 已报废
- 已完成

如果客户需要退回旧件，系统可以显示：

- 退回仓库
- 收件人
- 电话
- 地址
- 邮政编码

客户也可以填写退回物流单号。


八、案例内部沟通

每个售后案例内部希望有一个留言/聊天功能。

客户可以直接留言。

例如：

“I replaced the motor, but the problem still exists.”

公司售后人员可以直接回复。

双方回复时都可以继续上传：

- 图片
- 视频
- PDF
- 诊断文件

所有沟通内容自动保存到该案例中。

这样可以减少售后信息分散在：

- WhatsApp
- 微信
- Email

不同软件里面的问题。


九、内部审批

部分售后案例需要公司内部审批。

建议流程：

客户提交案例
→ 售后初审
→ 技术确认
→ 负责人审批
→ 批准补发零件
→ 仓库发货

审批人员可以选择：

- 同意
- 拒绝
- 退回补充资料

如果选择拒绝或退回，需要填写原因。


十、通知功能

案例发生重要变化以后，希望系统自动发送通知。

例如：

客户新提交案例
→ 通知售后人员

售后要求补充资料
→ Email 通知客户

客户补充资料
→ 通知售后人员

审批通过
→ 通知客户

配件发货
→ 自动发送物流信息给客户

案例完成
→ 通知客户

第一版至少需要支持 Email 通知。

后期可以考虑接入 WhatsApp。


十一、客户账号管理

公司后台可以创建不同经销商账号。

例如：

- 英国经销商
- 法国经销商
- 西班牙经销商
- 巴西经销商
- 墨西哥经销商

每个经销商公司下面可以创建多个员工账号。

例如：

Built Bikes

下面可以有：

- Chris
- Service Team
- Sales Team

这些账号属于同一个公司，可以根据权限查看公司自己的售后案例。

不同客户公司的数据必须隔离。


十二、后台 Dashboard

公司后台首页希望可以看到售后概况。

例如：

- 待处理案例数量
- 审核中案例数量
- 等待客户回复案例数量
- 待发货案例数量
- 已发货案例数量
- 本月完成案例数量
- 总案例数量

点击数字后，可以直接进入对应案例列表。


后期希望增加统计分析：

- 不同车型售后案例数量
- 不同车型售后率
- 不同部件故障数量
- 电机故障率
- 电池故障率
- 仪表故障率
- 不同国家售后数量
- 不同客户售后数量
- 平均案例处理时间
- 每月新增售后案例
- 每月完成案例数量


十三、权限管理

建议采用角色权限管理。

不同角色看到的内容和可操作范围不同。

例如：

客户：

只能查看自己公司的售后案例。

销售：

只能查看自己负责的客户。

售后：

可以处理售后案例。

技术：

可以填写技术维修方案。

仓库：

只能查看需要发货的信息并填写物流。

管理员：

可以查看和管理所有数据。


十四、数据安全

需要保证：

1. 不同客户之间的数据完全隔离。

2. 客户不能看到其他客户：

- 车辆信息
- 售后案例
- 联系人
- 价格
- 发货信息

3. 重要操作需要留下操作日志。

4. 删除案例或修改重要信息最好需要管理员权限。


十五、后期扩展

售后系统后期希望可以与公司的整车扫码溯源系统打通。

整车扫码溯源系统中：

车架二维码 = 整车唯一 ID。

每辆 e-bike 绑定：

- 车架
- 电机
- 电池
- 仪表

以后客户创建售后案例时：

输入车架号
或者
扫描车架二维码

系统自动读取这辆车的信息：

- 产品型号
- 电机 SN
- 电池 SN
- 仪表 SN
- 生产日期
- 入库时间
- 出库时间
- 所属经销商

客户只需要填写故障问题和上传图片即可。

这样售后系统和整车溯源系统最终可以共用同一套车辆数据库。


十六、第一阶段建议开发范围

第一版不需要一次把所有功能全部开发完成。

第一阶段优先完成以下主流程：

客户注册/登录
→ 客户账号管理
→ 新建售后案例
→ 客户填写车辆和故障信息
→ 上传图片/视频/文件
→ 提交案例
→ 后台查看案例
→ 审核案例
→ 添加维修方案
→ 修改案例状态
→ 补发零件
→ 填写物流信息
→ 客户查看处理进度
→ 案例完成
→ 保存完整历史记录
