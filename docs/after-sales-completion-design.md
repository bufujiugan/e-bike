## 已具备的基础与需要纠正的边界

当前已具备草稿、提交、开始审核、技术方案、审批、处理、补发计划、实际发货、解决、归档，以及留言、不可删除的审计历史、代理商范围检查、授权附件下载。状态变更、留言、发货和附件写入共用案例行锁，重要操作与审计原子提交。

`bike_sys_user.agent_id` 已允许多个 AGENT 账号绑定同一代理商，`UserServiceImpl.validateBindings` 会核验代理商启用状态。售后查询和资源访问按 `agent_id` 隔离，因此“一个经销商多个员工完全未实现”并不准确。当前缺少完整公司资料、公司成员专用管理页面、销售负责范围，以及代理商与业务客户两类主数据的明确关系；不能为了补齐文档而再造一套互相矛盾的 company ID。

建议第一版把现有 `bike_agent` 明确定义为经销商公司，继续复用 `user.agent_id` 作为员工归属。`bike_customer` 保留交易收货客户语义，售后外部账号不得通过随意指定 `customer_id` 扩大数据范围。已有的车辆当前出库归属验证继续保留。

## 最小下一批：公司资料、销售范围、案例快照与派单

这一批先形成后续审批、物流和 Email 都能使用的客户与负责人基础。已有多账号归属继续使用 `agent_id`，不增加第二个外部身份域。

### 数据迁移

主任务已分配 V29；不得修改已应用的 V23/V26。V29 四镜像冻结哈希为 `FEEEE8BEE8115BEF678C2F1BFF703F16A7F8A272FDA819D0C3AAC5058E7F44F8`。

1. 新增 `bike_after_sales_company_profile`，以 `agent_id` 为主键，保存联系人、电话、Email、国家、省市、地址和邮编；无 profile 时回退公共 agent 联系人和电话。此方式不改公共主数据写权限。国家采用 ISO 两位码，详细地址有明确长度上限。旧记录允许空值。
2. 新增 `bike_after_sales_sales_agent`：`sales_user_id`、`agent_id`、`enabled`、更新操作者与时间；二者联合唯一。只允许启用且有售后读取权限的内部 WEB 用户作为销售，外部或 PDA 账号不可绑定为销售负责人。关系变更写审计。
3. 新增 `bike_after_sales_case_contact`，以 `case_id` 为主键保存公司名称、联系人、电话、Email、国家、省市、地址、邮编、负责人姓名快照及 `end_customer_purchase_date`。旧案例回填当前可确定的名称/联系人/电话，并以 `MIGRATED_CURRENT` 标识迁移快照；缺失 Email/地址保留空值，不伪造历史资料。未来新案例默认复制当时资料。
4. 复用案例 `assignee_id`，加索引；迁移前先核验历史 ID 是否存在。关联用户只停用不物理删除，保留历史显示名快照或审计内容。
5. 新增 `AFTER_SALES_SCOPE_ALL`、`AFTER_SALES_ASSIGN`、`AFTER_SALES_COMPANY_MANAGE` 和销售只读角色。迁移为现有内部售后/技术/仓库角色授予业务所需范围权限，避免升级后意外失去历史权限。仅有 READ 的自建内部角色不应自动读取全部公司；默认限定销售映射，无映射为空列表。

### 范围与接口规则

- 外部账号优先限定自己的 `agent_id`，即使误授内部角色或全部范围权限也不能跨公司。PDA 始终拒绝售后入口。
- 内部有全部范围权限的账号访问全部案例；其余内部 READ 账号必须命中有效销售映射。外部公司员工和销售范围限定都应从认证上下文计算，API 不接收可覆盖范围的参数。
- 统一 `AfterSalesAccess` 与 mapper 范围片段，覆盖列表/count、单条案例、附件下载、历史、客户选项和统计。单条拒绝与列表隐藏同时验收。
- 管理接口提供公司联系资料修改、公司成员查询、销售负责公司配置和派单。派单只允许具有 ASSIGN 权限的内部账号；候选用户必须启用、有 READ 和 TECH/REVIEW 权限且不是外部/PDA。保存时还检查目标具备该公司范围，派单本身不增加数据权限。
- 公司资料/销售关系变更记录走独立 `/api/after-sales/companies/{id}/history`，需要内部 COMPANY_MANAGE 和当前公司范围，返回最近200条动作、操作人和时间；不给普通销售或外部员工读取管理审计JSON。
- 草稿默认带出公司联系快照；有权的创建者可纠正该案例联系人地址，但不可修改公司归属。已提交案例修改联系快照必须内部专用动作与原因审计；已发运记录保留独立收货快照。
- 列表和详情显示售后负责人姓名；负责人停用不抹掉历史，重新派单有可查记录。

### 页面最小交付

售后工作台增加公司联系资料入口；内部可编辑联系资料、配置负责销售、查看公司员工及管理变更记录，非管理角色只读公司联系资料。员工创建/停用仍复用既有用户管理入口，专门的公司成员创建与筛选不在本批范围。售后新建表单显示自动带出的联系人资料和两种购买日期，详情显示案例联系快照。列表增加负责人列，内部有权限者可派单，销售仅显示自己负责公司的案例。

| 场景 | 通过标准 |

| 公司 A 两个员工、公司 B 一个员工 | A 员工按权限共享 A 案例和客户附件；任何路径不能读取 B 案例、附件、选项、联系人或统计。 |

| 联系资料快照 | 新案例默认复制资料；之后公司资料变化不改旧案例，旧案例有权限的纠正产生审计。 |
| 派单 | 可选启用内部售后员工；外部/PDA/停用账号不可派；并发派单无丢失审计，终态规则明确。 |
| 升级兼容 | 旧库升级、新空库初始化和原售后全回归均通过；既有自建角色授权变化有明确迁移说明。 |

## 后续批次顺序

1. **查询与 Dashboard**：依赖范围、快照、负责人字段；先落地明确可统计的状态和过滤条件，再做点击钻取。
2. **结构化方案与审批**：增加方案版本、技术确认、负责人结论、配件清单和收费责任；审批与发运必须绑定同一版本。
3. **发运与旧件退回**：复用公司地址作为默认值但发运单独快照；每条配件有独立退回流程，收货/检测/报废均记录操作者和时间。
4. **Email**：业务事务写 outbox，提交后独立派发，按业务事件唯一键去重；失败重试和人工重发可见。验收先用专用测试邮箱/捕获服务，真实外发前由用户明确授权具体发送范围。

两轮最终验收要按完整需求矩阵执行。附件或上述单个批次通过，不代表整个售后系统或全项目完成。
